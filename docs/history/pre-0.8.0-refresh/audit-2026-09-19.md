## Execution and performance

No setInterval polling and no continuously running JavaScript animation loop were found. requestAnimationFrame batches event-driven work; it does not recursively run a permanent loop.

- Continuous visual work while visible: the EKG scan/trail and alert marquee are CSS animations; effect lights animate during their flash window. SVG stroke/filter work still costs browser painting. Reduced-motion mode stops these animations. Minimized HUD does not attach its body, so these visuals are not painted.
- Timers: one API message expiry timer, one indicator expiry timer, a legacy-message timer, and a 15-second timeout per outstanding remote combat request. These are one-shot, not polling.
- Hover DV: triggers on hover, relevant token/item updates and selection changes. Guarded for relevant actors; async revision checks prevent stale tooltips. Table requests are deduplicated within one refresh, but not by a persistent module cache across refreshes (Foundry may cache internally).
- Token HUD: native render/right-click actions and repositioning while its HUD is open. Pan/zoom handlers are gated.
- Combat mechanics: attacks, Evasion, damage and critical injuries run on explicit actions. GM-coordinated defense/damage requests use one serial queue.
- Chat scrolling: ResizeObserver watches the latest updated resolution card, with prior observers disconnected on replacement; it is not a scan of all cards every frame.
- Startup: one pass over loaded chat messages for pending alerts and, on the authoritative GM, actors/scene tokens for migration.

Main inefficiencies:
1. combat-resolution.ts:421 scans all loaded chat messages and rerenders all pending exchanges on every actor update and item create/update/delete, regardless of which actor/item changed. This scales with total chat history plus pending-card count, on every client. Several document writes in one action can trigger several passes.
2. eye-hud.ts:109 schedules a refresh for unrelated chat messages. render at :203 removes and recreates the entire HUD. Browser reproduction confirmed an ordinary unrelated chat event replaces the HUD root. This restarts animations, can lose focus, and performs layout measurements.
3. Disabling the HUD is checked after actor conditions and pending attacks are collected. Minimizing still constructs the detached medical body. These are avoidable event-driven costs, not continuous CPU loops.
4. Actor indicator maps retain entries for previously viewed actors throughout a session; there is no production call to resetMonitor. Small bounded-by-visited-actors overhead in ordinary use, worth cleanup for long GM sessions.

No live FPS/CPU measurements were taken. The source suggests low idle scripting cost but avoidable burst work in active combat/large histories. A numerical CPU percentage would be speculation.

## Confirmed correctness findings

### High: concurrent attack LUCK spending can lose deductions

native-combat.ts:78 reads LUCK then writes the remaining value. This is used outside the GM defense queue (combat-resolution.ts:362). attack-menu.ts:43 only locks the current client, not other clients or defense workflows.

Reproduced with delayed mocked actor writes: two concurrent spends of 2 from 5 leave 3, instead of 1. The same actor attacking and defending on separate clients needs coordinated resource spending. Ammo confirmation also needs a concurrent-client review.

### High: critical-injury click guard ends before native injury creation completes

critical-injury.ts:61 awaits the native sheet method, but the inspected CPR source at src/modules/actor/sheet/cpr-actor-sheet.js:1231 starts table.draw(...).then(...) without returning/awaiting that chain. The module's per-button rolling guard (damage-flow.ts:259) therefore releases before the actual draw/item creation completes.

Reproduced by evaluating that native method with an unresolved mock draw promise: the method returns before the draw completes. Rapid clicks can start extra injury rolls. The guard is also per rendered button/client rather than per recipient operation. Keep deliberate later rerolls possible while preventing overlapping executions.

### Medium: simultaneous status-picker edits overwrite one another

damage-flow.ts:93 saves the entire selection supplied by a picker without checking the selection/version that picker opened with.

Reproduced: two pickers start from the same selection; one saves Prone, the other saves Blind; the final selection is only Blind. The second save is accepted without warning. Add an expected-version/expected-selection check or edit individual slots deliberately.

### Medium: selected-target damage deduplication remembers only the latest application

damage-flow.ts:143 checks only damage.applicationId. Reproduced IDs A, B, A: native damage runs three times. A duplicate of the most recent request is safe, but an older duplicate after another application is not.

This is a retry/replay edge case, not a request to prevent intentional repeat damage. Fresh IDs must continue to allow the user to reapply damage.

## Additional review priorities

- Attack-start failure recovery: ammo confirmation and LUCK deduction happen before dice/card creation. A later failure can consume resources without leaving a usable exchange card. No attack-start recovery record is present.
- GM handover: the queue and claims exist in one GM client's memory. Disconnect/election during an in-flight write needs a real two-GM test; one-client fixtures do not establish failover safety.
- Native damage capture temporarily wraps CPRChat.RenderDamageApplicationCard and uses a proxy actor. The wrapper has identity checks and restoration, but compatibility with other wrappers/modules needs live testing.
- Critical injury code uses a private sheet method; Token HUD subclasses, native roll internals and exact template selectors are other version-sensitive integrations.
- Undo retains the native actor/token-ID lookup, not an explicit scene-token UUID operation. Test synthetic actors and scene changes before treating undo identity as verified.
- HUD messages are session-only and socket delivery is best-effort. A GM remote send returns an ID without a receipt; offline replay is intentionally absent. The normal API restricts remote calls to GMs, but this is not an authenticated/private messaging service.
- The current message selection persists when a new message arrives. A new incoming attack can sit behind an already-selected message. Decide whether attacks should interrupt selection or visibly mark unread messages.
- Metadata wording: client settings are browser/client-local, not account-synchronized User flags. They do not follow users across devices.
- Documentation has accumulated contradictory historical descriptions: thrown rename versus Used marker, hidden-when-empty versus always visible, old preview names, single alert versus message queue. BACKLOG can preserve history; IMPLEMENTED_FEATURES should be rewritten as current behavior.

## Verification

- pnpm check passed: TypeScript plus manifest/source asset validation.
- All 8 existing test files passed: 60 named node:test cases, the Biomonitor assertion script, and 3 browser-fixture scripts.
- Additional in-memory audit probes reproduced the LUCK lost update, status lost update, old application replay, native injury early return and unrelated-chat HUD rebuild. These probes assert observed defective behavior; their successful completion does not mean the bugs are fixed.
- No production source was changed during this audit. Test runs regenerated their normal preview artifacts.
